# 统一外设控制台 · 设计方案 v0.1

> 目标：把 ATK / 迈从 MCHOSE / 罗技 Logitech / 狼蛛 AULA 四个品牌的驱动能力合并进一个软件。
> 本文基于对 4 个安装包的实际拆解 + 公开协议实现调研。

---

## 0. 先纠正一个前提

这 4 个都不是"驱动"（不装内核驱动、不注册系统服务级 driver）。

| 实际形态 | 说明 |
|---|---|
| 用户态 HID 配置器 | 通过 HID Feature / Output Report 直接与设备芯片通信 |
| 通信协议 | 各厂商私有，但**不走内核**，普通用户态程序即可收发 |

所以"合并驱动" = **合并 HID 协议层 + 合并 UI + 统一能力模型**。没有内核开发工作，也不存在驱动签名问题。这是好消息：难度比想象低一个量级。

第二个好消息：**4 个品牌里有 3 个的协议已被社区完整逆向并开源实现**，不需要从零抓包。

## 1. 四个安装包的技术画像

| 品牌 | 安装包 | 封装 | 主程序形态 | 设备通信 | 协议现状 | 逆向难度 |
|---|---|---|---|---|---|---|
| **ATK** | atk-hub-3.2.33.exe（143MB） | NSIS 3.04，**需管理员** | Web 前端 + WebHID | Vendor page `0xFF05`，63 字节 output report 8；COMPX 设备 `0xFF04` 16 字节帧；键盘 `0xFF60` VIA/QMK | 高：`atkctl` 已公开 PROTOCOL.md；`Tubatools.AtkHub` 反编译 KeyLinkerlib.dll 已覆盖 167 款鼠标 | ★★☆ |
| **迈从** | MCHOSE_HUB_installer.zip → M HUB installer.exe（161MB） | NSIS 3.04，需管理员 | Web 前端 + WebHID | SINOWEALTH `0x41E4` Feature Report 9（读 519 / 写 519 字节）；键盘 `0x3837` | **极高**：官网 `mchose.com.cn` 前端是未混淆 Vite 产物，协议逻辑直接可读；多个仓库已有完整文档 | ★☆☆ |
| **罗技** | lghub_installer.exe（71MB） | WiX Burn（.NET 4.7.2） | Electron + 后台 agent | HID++ 2.0；另有本地 `ws://localhost:9010` JSON API（`{path,verb}`） | 高：HID++ 有公开文档；OpenRGB / libratbag / logiops / Solaar 均已实现 | ★★☆（功能面最宽） |
| **狼蛛** | 狼蛛_神光同步_V1.0.12_Setup.exe（63MB） | Inno Setup 6 | 原生（Qt/Delphi） | HID Feature Report id 7，8 字节；2.4G 走 65 字节 output report + 厂商标封信封 | 中高：`MiaHUB`（Tauri+Rust）、`AULA-F87`、`AULA-F108` 三个开源项目已实现灯效/改键 | ★★★ |

### 关键发现

1. **ATK / 迈从 / 狼蛛 同源度很高**：都是国产方案商芯片（Sinowealth / CompX / BY 系），传输层几乎一致 —— 一个 `HidTransport` + 分片/信封处理就能覆盖三者。
2. **ATK 和迈从已经是网页驱动**（WebHID）。这意味着它们的协议是"浏览器可直连"的，抓包和复现成本极低。
3. **罗技反而是最规范的**：HID++ 2.0 有公开规范，但设备型号最杂、部分新设备有校验/加密。
4. 四个安装包共 438MB，其中绝大部分是 UI 资源、多语言、云同步、遥测。**合并后的真实核心可能只有 30~50MB。**

## 2. 三条技术路线

| | A. 统一外壳 | B. 协议重写（真合并） | **C. 混合（推荐）** |
|---|---|---|---|
| 做法 | 一个壳子内嵌/调度 4 个官方 exe | 自己实现全部 HID 协议 | 能干的自研，干不了的内嵌官方 Web 驱动 |
| 开发量 | 1~2 周 | 3~6 人月 | 2~4 人月 |
| 覆盖度 | 100% | 取决于逆向进度 | 100%（兜底） |
| 体验 | 差（4 个窗口/4 份资源） | 最好（真统一） | 好 |
| 风险 | 几乎为零 | 中（砖机、协议变更） | 低 |
| 结论 | 只适合做"过渡版" | 目标终态 | **先做这个** |

**推荐 C，并设置降级阶梯**：

```
自研协议（首选）
  ↓ 某设备未适配 / 某功能未实现
内嵌官方 Web 驱动（webview，仅限有网页版的品牌：ATK / 迈从）
  ↓ 只有桌面版（罗技 / 狼蛛）
调用官方本地接口（G HUB ws://9010）或提示用户装官方软件
```

## 3. 架构设计

### 3.1 分层

```
┌──────────────────────────────────────────────┐
│ UI 层        React + TS，Tauri WebView        │
│   设备墙 / 灯效画布 / 改键 / 宏 / 设置         │
├──────────────────────────────────────────────┤
│ 应用服务层                                    │
│   Profile 引擎 · 灯效合成引擎 · 宏转换器       │
│   场景自动切换 · 托盘 · 热插拔 · IPC           │
├──────────────────────────────────────────────┤
│ 统一能力模型 Capability Model（核心）         │
│   语义 API：DPI / 回报率 / 灯效帧 / 键位 / 宏  │
├──────────────────────────────────────────────┤
│ 驱动适配层 Providers（可插件化）              │
│   atk · mchose · aula · logitech              │
├──────────────────────────────────────────────┤
│ 传输层 HidTransport                           │
│   hidapi · 分片重组 · 2.4G 信封 · 节流 · 互斥  │
├──────────────────────────────────────────────┤
│ 设备发现 DeviceDiscovery                      │
│   SetupAPI / hidraw 枚举 · VID/PID/CID 匹配   │
└──────────────────────────────────────────────┘
```

### 3.2 技术栈选型

| 选项 | 结论 |
|---|---|
| **Tauri 2 + Rust**（推荐） | 安装包 ~10MB，内存 ~60MB，`hidapi` 生态成熟，可做托盘/后台/开机自启。有 `MiaHUB`（狼蛛）现成参考 |
| Electron + node-hid | 开发快、可直接复用厂商 WebHID 前端 JS，但包体 150MB+，本身就是"第二个 G HUB" |
| .NET 8 WPF | 有 `Tubatools.AtkHub` / `offline-mchose` 现成参考，Windows 生态好，但跨平台差 |

选 **Tauri 2 + Rust + hidapi** 作为终态，理由：这个项目的核心价值是"轻"，再用 Electron 就自相矛盾了。

> **v0.2 修正（已实施）**：第一阶段的核心层用 **TypeScript + node-hid** 落地，而不是 Rust。原因有三：
> ① 本机没有 Rust / MSVC 工具链，而验证架构不需要写完整的桌面壳；
> ② ATK 与迈从的官方驱动本身就是 Web 前端，TS 能直接对照它们的逻辑；
> ③ 核心层（类型、能力模型、Provider、传输）**零 UI 依赖**，先用 TS 跑通，桌面壳可以后接（Tauri sidecar 或 Electron 均可）。
>
> 代价也明确：如果最终上 Tauri，传输层与协议层要重写一遍。这是"先跑通再优化"的自觉选择，不是遗忘。

### 3.3 核心抽象

```rust
trait Provider {
    fn name(&self) -> &str;
    fn probe(&self, dev: &HidDeviceInfo) -> Option<DeviceMatch>;
    fn open(&self, m: &DeviceMatch) -> Result<Box<dyn Session>>;
}

trait Session {
    fn caps(&self) -> &Capabilities;          // 决定 UI 显示哪些控件
    fn info(&self) -> DeviceInfo;             // 电量/固件/连接模式
    fn dpi(&self) -> Result<DpiTable>;
    fn set_dpi(&self, t: &DpiTable) -> Result<()>;
    fn apply_frame(&self, f: &LightingFrame) -> Result<()>;   // 只收"每键RGB帧"
    fn keymap(&self, layer: u8) -> Result<KeyMap>;
    fn set_keymap(&self, layer: u8, m: &KeyMap) -> Result<()>;
    fn commit(&self) -> Result<()>;           // 写入板载内存
}
```

**UI 不认品牌**。每个控件由 `caps()` 动态渲染：设备支持 DPI 才显示 DPI 页，支持触发行程才显示磁轴页。加新品牌 = 加一个 Provider + 一份 JSON，UI 零改动。

## 4. 统一能力模型（最难也最关键）

### 4.1 三层抽象

| 层 | 内容 | 谁消费 |
|---|---|---|
| 语义层 | DPI、回报率、灯效、键位、宏、触发行程、电量 | UI |
| 设备描述层 | 每个 VID/PID 一份 JSON：按键矩阵、灯区拓扑、能力位、协议版本 | Provider |
| 协议层 | 原始字节帧 | 传输层 |

### 4.2 灯效：这是"合并"的真正价值

**设计原则：协议层只接受"每键 RGB 帧"，不做效果。**

- 效果引擎（呼吸/波浪/音频律动/联动）全部在应用层用统一时间轴 + 图层合成
- 30fps 合成一次，广播给所有设备的 `apply_frame()`
- 结果：**4 个品牌的灯可以真正同步**，而不是各跑各的

厂商原生模式（如狼蛛的"随波逐流"、ATK 的灯效库）作为"兼容模式"保留，但不参与统一同步。

```
效果引擎 (图层合成) → LightingFrame{vendor-agnostic} → Provider 编码 → HID 帧
                                              ↑
                              每个品牌一套"帧→协议"编码器
```

### 4.3 键位映射：不能直接搬

不同品牌键位矩阵、层数、键码体系都不同。方案：

- 统一标识用 **HID Usage Code + 物理坐标 (row, col)**
- 每品牌 JSON 提供 `matrix_map`：`(row,col) → usage`
- 跨品牌导入配置时按 usage 对齐，物理坐标兜底
- 宏：统一内部 AST，写入时转成厂商格式（狼蛛是 XML，ATK 是二进制步骤脚本）

## 6. 技术难点与对策

| # | 难点 | 对策 |
|---|---|---|
| 1 | 官方软件独占 HID 句柄 | 启动时检测并提示关闭，**不做强杀**；提供"互斥模式"开关 |
| 2 | 有线 / 2.4G / 蓝牙 三套协议 | `Transport` 抽象，每模式独立 codec；蓝牙通常只读电量 |
| 3 | 写入频率限制（狼蛛需 ≥110ms 间隔） | 全局节流器 + 每设备 `quirks.min_write_interval_ms` |
| 4 | **砖机风险** | 白名单 PID + 写前读校验 + 只写已验证偏移；未知回包立即中止，不做"猜测式写入" |
| 5 | 固件更新 | **明确不做**。签名/校验复杂且失败即废，交给官方软件 |
| 6 | 罗技新设备校验/加密 | 优先 HID++ 标准路径；不支持则降级到 G HUB 本地 API 或 OpenRGB |
| 7 | 多设备灯效同步抖动 | 统一时钟，一帧广播；帧率上限 30fps；写入失败设备自动降频 |
| 8 | 游戏反作弊误判 | 只写设备内存，不做输入注入、不挂全局钩子 |
| 9 | 法律与商标 | 仅做互操作实现，不打包厂商二进制、不使用其商标与素材；开源需注明非官方 |
| 10 | 协议随固件漂移 | 设备 JSON 带 `firmware_range`；未知固件降级为只读 |

## 8. 需要你确认的 5 件事

1. **具体设备清单**（型号 + 有线/2.4G/蓝牙）。协议工作量几乎完全由这个决定。
2. 能否接受"个别设备走内嵌官方 Web 驱动"的降级方案？
3. 范围边界：只要 灯效 + 基础参数（DPI/回报率），还是要 改键 + 宏 + 板载配置？**固件更新建议永久排除。**
4. 人力：你一个人做，还是有团队？Rust / C 经验如何（决定选 Tauri 还是 Electron）。
5. 开源还是自用？开源可以复用 `MiaHUB` / `atkctl` / `offline-mchose` 的协议文档，但要处理 GPL/MIT 差异。
